# JobTracker — Anti-Corruption Layer for the Persistence Dependency

A refactoring plan, not an implementation. Nothing in `src/` is modified by this document. Every citation below
was read in the file at the line given.

Companion to [`01-domain-distillation.md`](./01-domain-distillation.md), which ranked *"extract the follow-up
policy"* as refactoring #1. This document addresses a different axis: not *where the domain rule lives*, but
*which external library's shape the whole codebase is built out of*. The two are complementary — §4 shows why
the ACL is the natural home for the policy that document asks for.

| Axis | Supabase | zod | dnd-kit |

| (c) Docs declare it replaceable? | **Yes, three times** — `prd.md:103`, `prd.md:191`, `roadmap.md:82` say auth is *"provider-agnostic"*; `infrastructure.md:67` says *"Keep Supabase as the exclusive data layer to preserve portability"* | No claim | No claim |
| (c) Docs declare a boundary the code breaks? | **Yes** — `AGENTS.md:65` | No | No |

### Selection: `@supabase/*` + `database.types.ts`

It wins every axis, and it is the only candidate where **stated intent and actual code diverge**. That
divergence is the strongest available signal, and there are two independent instances of it:

1. **`AGENTS.md:65`** declares: *"`src/lib/` — **pure utilities only** (no Supabase, no domain logic)"*. The
   very next line, **`AGENTS.md:66`**, declares: *"`src/lib/supabase.ts` — SSR client"*. The rules file
   contradicts itself across two consecutive lines. That contradiction is not sloppiness — it is the symptom of
   a missing layer. There is nowhere else to put the client, so it went into the directory that forbids it.

2. **`infrastructure.md:67`**: *"Vendor lock-in deepens with each Cloudflare primitive… Keep Supabase as the
   exclusive data layer to preserve portability."* The document reasons carefully about lock-in on the compute
   side while the data side was allowed to become the application's universal type system.

3. **`prd.md:103`**, **`prd.md:191`**, **`roadmap.md:82`** all assert the auth model is *provider-agnostic*
   because *"RLS uses `auth.uid()`"*. That is true of the **database** and false of the **application**:
   `src/env.d.ts:3` binds `App.Locals.user` to `@supabase/supabase-js`'s `User` type, so swapping the auth
   provider changes a type that 10 files depend on.

zod is a duplication problem worth fixing (Phase 4 below folds it in). dnd-kit is fine.

## Step 3 — Diagnosis

### 3.1 The declared boundary vs. the code

| Declared | Cited | Reality |
| --- | --- | --- |
| *"`src/lib/` — pure utilities only (**no Supabase**, no domain logic)"* | `AGENTS.md:65`, restated `README.md:95-96` | `src/lib/supabase.ts` (the SDK), `src/lib/database.types.ts` (the vendor codegen), `src/lib/config-status.ts:11-19` (vendor name in UI copy) all live in `src/lib/` |
| *"`src/lib/services/` — Supabase queries **+ domain orchestration**"* | `AGENTS.md:65` | The services contain no domain orchestration. All 9 functions in `src/lib/services/applications.ts` are one query each; the only rule present is the predicate at `applications.ts:79-80` |

Each emits the identical string `"Supabase nie jest skonfigurowany."`. A vendor name is in the product's Polish

**D2 — the client type alias, ×2**

`src/lib/services/applications.ts:5` and `src/lib/services/notes.ts:4` both declare
`type Client = NonNullable<ReturnType<typeof createClient>>`.

**D3 — `z.uuid()`, ×5** — `[id].ts:10`, `archive.ts:9`, `notes/index.ts:10`, `notes/[noteId].ts:10`,

**D4 — re-narrowing the generated type, ×2 (and growing)**

The codegen widens CHECK-constrained columns to bare `string` — `src/lib/database.types.ts:80` gives
`status: string`, `:82` gives `work_mode: string | null`, even though the migration constrains both. Every
consumer must re-narrow:

- `src/pages/dashboard.astro:22-23` — a runtime `includes` guard plus `row.status as ApplicationStatus`
- `src/components/board/EditApplicationDialog.tsx:28` — `application.work_mode as WorkMode | null`

The domain vocabulary is defined at `src/lib/validation/applications.ts:3-4` and enforced in SQL, but the type
that flows through the app knows neither. **Two casts today; one per new consumer forever.**

**D5 — a 40-line hand-rolled fake of the vendor's query builder**

`tests/unit/services/applications.test.ts:11-45` builds a chainable spy imitating
`.from().select().eq().is().order().maybeSingle()` because there is no port to substitute. Note the tension
with `AGENTS.md:11`, which lists *"mock the Supabase client in tests"* under 🚫 **Never** (scoped there to RLS
suites, where the client is the SUT). A port removes the need for the imitation entirely.

### 3.3 Cross-boundary leaks

**L1 — the persistence row is the wire contract.** `src/pages/api/applications/index.ts:34`,
`[id].ts:45`, and `[id]/archive.ts:30` all return `{ application: row }` where `row` is
`Database["public"]["Tables"]["applications"]["Row"]`. Per `src/lib/database.types.ts:69-83` that row includes
`user_id: string`. **The API ships the caller's internal user UUID back to the browser on every create,
update, and reject.** It is the caller's own id, so this is not a data-isolation failure — but it is a column
that exists purely for RLS, published in a public contract for no reason. Notes do the same:
`notes/index.ts:30,68` and `notes/[noteId].ts:51` return rows carrying `user_id` and `application_id`
(`database.types.ts:38-44`).

Because the shape is generated, **a future `db:types` run silently changes the public API**. Add a column to
`applications` and it appears in the JSON response and in `ApplicationRow`, with nothing in between to notice.

**L2 — the DB schema is the React prop type.** `src/components/board/KanbanCard.tsx:40` declares
`application: ApplicationRow`. The island then reads snake_case persistence columns directly:
`application.last_action_at` (`KanbanCard.tsx:137,138,139`), `application.work_mode`
(`KanbanCard.tsx:208,210`), `application.recruiter_contact` (`CardDetailDialog.tsx:62,64`),
`row.archived_at` (`archive.astro:41,43`). The UI receives a database record and does the interpretation
itself.

**L3 — the client fabricates database rows.** `src/components/board/KanbanBoard.tsx:76` and `:110` build
optimistic state as `{ ...card, status: to, last_action_at: movedAt }` — the browser writing a
`last_action_at` value that, per `01-domain-distillation.md` I-03 and `prd.md:164`, only a DB trigger is
allowed to set. The client's guess is thrown away on reload, but the UI is guessing at a column the domain
declares DB-owned.

**L4 — vendor error strings reach the user, in English.** `src/pages/api/auth/signin.ts:16` redirects with
`error.message` taken straight from the Supabase `AuthError`; `signin.astro:4` reads it from the query string
and `SignInForm` → `ServerError.tsx:12-13` renders it verbatim. `AGENTS.md` requires Polish user-facing copy;
here the copy is whatever the SDK emits.

**L5 — domain interpretation performed in the API layer.**
`src/pages/api/applications/[id]/archive.ts:33-42`: when the guarded UPDATE returns no row, the route issues a
*second* query (`getOwnedApplicationState`) and inspects `owned.archived_at !== null` to decide between 404,
"already rejected", and "cannot reject from Interesujące". That is the rejection rule being reconstructed from
raw columns at the HTTP boundary, one round-trip too late.

**What does *not* leak, stated precisely:** no React component imports any `@supabase/*` runtime value. Every
crossing is `import type` (`src/types.ts:1`, `src/env.d.ts:3`) or a locally-declared alias, so the SDK is
erased at build and **no Supabase code enters the client bundle**. `SUPABASE_URL` / `SUPABASE_KEY` are read
only from `astro:env/server` (`src/lib/supabase.ts:3`, `src/lib/config-status.ts:1`) and never reach the
browser. This is a **type- and shape-level leak, not a runtime bundle leak** — the secrets rule at
`AGENTS.md:11` is intact.

## Step 4 — ACL design

Two new directories. `src/domain/` holds knowledge; `src/infrastructure/` holds the one implementation that
knows Supabase exists.

```
    application-repository.ts ← the narrow port (§4.2)

src/infrastructure/supabase/
  client.ts                   ← moved from src/lib/supabase.ts — THE ONLY @supabase/* import
  database.types.ts           ← moved from src/lib/database.types.ts (db:types target updated)
  mappers.ts                  ← row ⇄ domain, the sole snake_case translator
  errors.ts                   ← PostgrestError / AuthError → domain errors, Polish copy

  note-repository.ts
  session-gateway.ts
```

### 4.1 `JobApplication` — the sole source of knowledge about the dependency's shape

A frozen value object. It is the only place that knows the column names, that `status` arrives as a widened
`string`, that `archived_at: null` means *active*, and that the wire format is camelCase.

```ts
// src/domain/application/job-application.ts

export interface JobApplicationProps {
  readonly id: ApplicationId;
  readonly owner: OwnerId;
  readonly source: string;
  readonly position: string | null;
  readonly company: string | null;
  readonly description: string | null;
  readonly salary: string | null;
  readonly workMode: WorkMode | null;      // narrowed — never `string | null`
  readonly recruiterContact: string | null;
  readonly status: ApplicationStatus;      // narrowed — never `string`
  readonly createdAt: Instant;
  readonly lastActionAt: Instant;
  readonly archivedAt: Instant | null;
}

export interface ApplicationDTO { /* camelCase, NO owner/user_id, dates as ISO strings */ }

export class JobApplication {
  private constructor(private readonly props: JobApplicationProps) {}

  // ---- persistence boundary: the ONLY snake_case in the domain ----------
  static fromPersistence(record: ApplicationRecord): JobApplication
  //   validates status ∈ applicationStatusValues        → else DomainDecodeError
  //   validates work_mode ∈ workModeValues | null       → else DomainDecodeError
  //   renames last_action_at → lastActionAt, etc.
  //   REPLACES the casts at dashboard.astro:22-23 and EditApplicationDialog.tsx:28

  static draftToPersistence(owner: OwnerId, draft: ApplicationDraft): ApplicationInsertRecord
  //   emits user_id; NEVER emits last_action_at (DB-owned — prd.md:164)

  changesToPersistence(changes: ApplicationChanges): ApplicationUpdateRecord
  //   whitelist only; last_action_at and created_at are structurally unreachable

  // ---- wire boundary ---------------------------------------------------
  toDTO(): ApplicationDTO          // drops `owner` → fixes leak L1
  static fromDTO(dto: ApplicationDTO): JobApplication   // used by React islands

  // ---- domain operations ----------------------------------------------
  get isArchived(): boolean                    // archivedAt !== null
  canBeRejected(): boolean                     // !isArchived && status ∈ {Zaaplikowano, Rozmowa}
  rejectionRefusal(): RejectionRefusal | null  // why not — absorbs archive.ts:33-42
  isEditable(): boolean                        // !isArchived — the missing guard, D-05
  requiresAction(now: Instant): ActionPrompt | null   // delegates to follow-up-policy.ts
  withOptimisticStatus(next: ApplicationStatus, at: Instant): JobApplication
  //   replaces the raw spread at KanbanBoard.tsx:76,110 — fixes leak L3
}
```

`ApplicationRecord` is a **hand-written interface in `src/infrastructure/supabase/mappers.ts`**, structurally
compatible with the codegen row. Codegen output is then an implementation detail of one file, and a stray
`db:types` run cannot silently reshape the public API.

`ApplicationNote` mirrors this with `fromPersistence` / `toDTO` (dropping `user_id` and `application_id`).

`Instant` is a thin branded ISO-8601 string. It exists so `lastActionAt` cannot be confused with an arbitrary
string, and so `01-domain-distillation.md` D-02/D-10 (the clock question) has exactly one place to be decided.

### 4.2 The narrow port

Domain code depends on this interface and nothing else. It has no Supabase types, no `PostgrestError`, no
`.from()`, no query-builder chaining.

```ts
  listActive(owner: OwnerId): Promise<JobApplication[]>;

  | { kind: "not-found" }

  | { kind: "not-found" }
```

```ts
  constructor(private readonly db: SupabaseClient<Database>) {}

  async listActive(owner) {
    const { data, error } = await this.db.from("applications")
      .select("*").eq("user_id", owner).is("archived_at", null)
      .order("created_at", { ascending: false });
    if (error) throw toDomainError(error);
    return data.map(JobApplication.fromPersistence);
  }

  async reject(owner, id): Promise<RejectOutcome> {
    // The guarded UPDATE stays — it is the concurrency-safe pattern already at
    // services/applications.ts:79-80 and is worth preserving verbatim.
    const { data, error } = await this.db.from("applications")
      .update({ archived_at: nowIso() })
      .eq("id", id).eq("user_id", owner)
      .is("archived_at", null).in("status", ["Zaaplikowano", "Rozmowa"])
      .select("*").maybeSingle();
    if (error) throw toDomainError(error);
    if (data) return { kind: "rejected", application: JobApplication.fromPersistence(data) };

    // The second query moves here from archive.ts:33-42. The HTTP layer stops
    // reconstructing domain state from raw columns.
    const probe = await this.db.from("applications")
      .select("status, archived_at").eq("id", id).eq("user_id", owner).maybeSingle();
    if (probe.error) throw toDomainError(probe.error);
    if (!probe.data) return { kind: "not-found" };
    if (probe.data.archived_at !== null) return { kind: "already-rejected" };
    return { kind: "not-rejectable", status: decodeStatus(probe.data.status) };
  }
}
```

### 5.3 Open questions resolved from the library's contract, and where each decision is coded

These are questions the current code answers implicitly, in the wrong layer. Each has one home in the ACL.

| Question | Resolution (from PostgREST / supabase-js behaviour) | Coded in |
| --- | --- | --- |
| A guarded UPDATE matching no row returns `data: null`, `error: null` — is that *absent*, *not-yours*, or *wrong-state*? | PostgREST cannot distinguish them; only a second read can. Today that read is issued by the HTTP route (`archive.ts:33`) | `SupabaseApplicationRepository.reject` returns a `RejectOutcome` union — `src/infrastructure/supabase/application-repository.ts` |
| `.maybeSingle()` vs `.single()` — `single()` errors (PGRST116) on zero rows, `maybeSingle()` yields `null` | Adapter uses `maybeSingle()` for lookups, `single()` only after INSERT where a row is guaranteed (as `services/applications.ts:150` already does) | `mappers.ts` + adapter methods |
| A `PostgrestError` is `{ code, message, details, hint }` — never a JS `Error` subclass; RLS denial surfaces as an empty result, not an error | Translate `code` to a domain error; never propagate `message` to the user | `src/infrastructure/supabase/errors.ts` |
| `AuthError.message` is English and version-dependent (`"Invalid login credentials"`, `"Email not confirmed"`) | Map `error.code` / `error.status` to an `AuthOutcome`; the Polish string is chosen by the domain — fixes leak L4 at `signin.ts:16` | `SupabaseSessionGateway` + `src/domain/ports/session-gateway.ts` |
| Generated `Row` types widen CHECK-constrained columns to `string` (`database.types.ts:80,82`) | Decode-and-validate once at the boundary; never `as`-cast downstream | `JobApplication.fromPersistence` — removes the casts at `dashboard.astro:23` and `EditApplicationDialog.tsx:28` |
| `getUser()` calls the Auth server; `getSession()` reads the cookie unverified | Keep `getUser()` (`middleware.ts:12`) — it is the correct choice; record the reason so it is not "optimised" away | `SupabaseSessionGateway.currentUser` |

Note the two *domain* questions this refactoring deliberately does **not** answer: the clock semantics
(`01-domain-distillation.md` D-02) and server-vs-client evaluation (D-10). Those are product decisions. The ACL
gives them one file to be decided in — `src/domain/application/follow-up-policy.ts` — instead of being
implicitly settled inside `src/lib/format.ts:30-39`.

## Summary

Supabase is the leaking dependency, and the leak is one of shape rather than of imports: `@supabase/ssr` is
imported exactly once, but the generated row type is re-exported as `ApplicationRow` at `src/types.ts:3` and
from there becomes the service return type, the JSON wire contract, the SSR page model, and the React prop type
across 28 files in five layers. Three documents assert what the code contradicts — `AGENTS.md:65` says
`src/lib/` contains no Supabase while `AGENTS.md:66` names `src/lib/supabase.ts` on the very next line,
`infrastructure.md:67` calls for portability of the data layer, and `prd.md:103`/`prd.md:191`/`roadmap.md:82`
call the auth model provider-agnostic while `src/env.d.ts:3` pins `App.Locals.user` to the SDK's `User` type.
The concrete costs are measurable: the client is constructed at 15 sites with the vendor's name repeated in
eight Polish error strings, `user_id` ships to the browser on every create/update/reject, the codegen's widened
`status: string` forces `as`-casts at `dashboard.astro:23` and `EditApplicationDialog.tsx:28`, the archive
route reconstructs a domain rule from raw columns at `archive.ts:33-42`, and a unit test hand-rolls 35 lines of
fake query builder because no port exists to substitute. Nothing vendor-specific reaches the client bundle —
every crossing is `import type` and the secrets rule at `AGENTS.md:11` holds — so this is a design defect, not
a security one. The remedy is a `JobApplication` value object owning every translation between column names,
wire format, and domain vocabulary; three narrow ports (`ApplicationRepository`, `NoteRepository`,
`SessionGateway`) returning discriminated outcomes instead of ambiguous nulls; and a single adapter directory
that is the only place `@supabase/*` may be named. Replacing the database afterwards touches 8 files in one
directory instead of 28 across five layers, with migrations, RLS suites, the JSON contract, and every component
untouched. The eight-phase plan is additive through Phase 3 and reversible at each gate, and it gives the
follow-up policy that `01-domain-distillation.md` ranked #1 the domain home it currently lacks.
